## 1. 한 줄 정의

**사주상담사가 고객을 접수한 순간부터 예약·상담 준비·실시간 풀이·기록·고객용 리포트·재방문까지 한 곳에서 처리하도록 돕는 상담사 전용 업무 플랫폼.**

엔진은 계산과 근거 정리, 초안 생성을 담당하고 상담사는 최종 해석·수정·검수·전달을 담당한다. 제품은 상담사를 대신해 운세를 확정하거나 고객에게 검수되지 않은 자동 해석을 직접 발행하지 않는다.

### 제품이 해결하는 핵심 문제

현재 상담사는 고객의 출생정보와 상담 목적을 받은 뒤 만세력책·참고서·메신저·캘린더·스프레드시트·문서 편집 도구를 오가며 다음을 반복한다.

1. 출생정보·시간 기준을 확인하고 명식을 계산한다.
2. 상담 목적에 맞는 근거를 찾고 과거 상담 맥락을 다시 읽는다.
3. 상담 중 질문이 바뀔 때 대운·세운·십신·합충형파해 등의 근거를 재조회한다.
4. 메모와 고객용 문장을 별도로 정리한다.
5. 상담 후 리포트를 다듬고 전달하며 다음 상담을 관리한다.

제품 가설은 **계산·검색·복사·정리 시간을 줄여 상담사가 고객과 대화하고 해석을 검수하는 시간으로 이동시키면 유료 가치가 발생한다**는 것이다.

## 2. 전략적 범위와 포지셔닝

### 2.1 초기 ICP

**우선 검증 대상: 1인 사주상담사**

선정 이유:

- 의사결정자가 사용자와 동일해 인터뷰와 베타가 빠르다.
- 예약·상담·리포트 작성의 전체 흐름을 한 명에게서 관찰할 수 있다.
- 다인 조직의 복잡한 배정·정산·조직 권한을 초기 범위에서 제외할 수 있다.
- 엔진의 시간 절감 효과를 개인 단위로 측정하기 쉽다.

다만 이는 확정 시장 선택이 아니라 **첫 검증 가설**이다. 다음 세그먼트는 1인 상담사에서 반복 수요와 지불 의사를 확인한 뒤 검토한다.

- 다인 역학원: 팀 권한, 배정, 지점, 정산이 필요하다.
- 인플루언서·콘텐츠 사업자: 대량 리포트, 브랜드, 고객 유입·결제가 중요하다.

### 2.2 하지 않을 것

- 상담사를 대체하는 무검수 자동 운세 서비스
- 초기부터 상담 고객을 모집하는 마켓플레이스·추천 알고리즘
- 초기부터 PG·에스크로·상담사 정산을 직접 운영하는 결제 중개
- 전문가 검수 전 콘텐츠를 상용 고객에게 자동 발행
- 처음부터 모바일 앱, 팀용 ERP, 다지점 운영까지 동시에 구축

### 2.3 차별화 가설

| 범용 예약/CRM | 이 제품 |
|---|---|
| 예약·결제·알림 중심 | 예약 맥락이 명식·질문·상담 세션으로 연결 |
| 범용 고객 메모 | 계산 근거, 내부 해석 메모, 고객용 표현 분리 |
| 단발 문서 | 고객 타임라인과 계산 버전이 보존된 재상담 맥락 |
| 자동 문장 중심 | 근거 → 상담사 초안 → 검수된 리포트 |
| 서비스 브랜드 예약 페이지 | 상담사 브랜드의 예약·리포트·공유 링크 |

## 3. 핵심 사용자와 사용 시나리오

### 3.1 핵심 사용자

**주 사용자 — 1인 사주상담사**

- 여러 채널로 상담 문의를 받는다.
- 고객의 출생정보와 질문을 직접 수집한다.
- 상담 전 준비와 상담 후 리포트를 혼자 처리한다.
- 빠른 조회는 원하지만 결과의 근거와 자신의 해석 통제권을 포기하지 않는다.

**보조 사용자 — 상담 고객**

- 예약·결제 안내를 받고 사전 정보를 입력한다.
- 상담 후 상담사가 검수한 리포트를 안전하게 열람한다.
- 자신의 정보와 공유 링크를 통제할 수 있어야 한다.

**후속 사용자 — 다인 역학원 관리자/상담사**

- 초기 MVP의 직접 대상이 아니다.
- 고객·예약 배정·권한·정산 요구를 별도 검증한다.

### 3.2 대표 시나리오

#### 상담 전

1. 상담사가 고객을 생성하거나 예약 링크로 고객 정보를 받는다.
2. 서비스 유형과 상담 목적을 선택한다.
3. 출생정보, 출생지, 시간 정확도, 시간 보정 기준을 확인한다.
4. 엔진이 명식·대운·세운과 경고를 계산하고, 상담 목적별 브리핑을 만든다.
5. 상담사는 근거를 검토하고 질문/준비 메모를 추가한다.

#### 상담 중

1. 예약/세션에서 고객의 명식, 상담 목적, 사전 답변, 과거 이력을 한 화면에서 확인한다.
2. 직업·재물·사업·연애·결혼·올해 운 등 질문을 선택한다.
3. 엔진은 질문과 관련한 근거, 시점, 패턴, 초안 문장을 보여준다.
4. 상담사는 자신의 해석을 메모하고 초안 문장을 수정하거나 제외한다.
5. 시간 미상·계산 기준·콘텐츠 경고는 결과와 함께 명확히 표시한다.

#### 상담 후

1. 상담사는 세션 메모, 핵심 결론, 후속 과제를 정리한다.
2. 고객용 문장을 검수하고 리포트 공개 범위를 선택한다.
3. 상담사 브랜드 HTML/PDF 링크를 발행한다.
4. 고객 열람·철회·삭제 요청을 처리한다.
5. 필요할 때 후속 예약 안내를 수동으로 보낸다.

## 4. 제품 구조

### 4.1 모듈

1. **워크스페이스/보안** — 상담사 계정, 고객 테넌트 분리, 세션, 권한, 감사 로그.
2. **고객/상담 CRM** — 고객 프로필, 동의, 출생정보, 상담 목적, 타임라인, 검색.
3. **서비스 카탈로그** — 상담 종류, 시간, 가격 표시, 사전 질문, 산출물, 취소 정책.
4. **예약/상태** — 가능 시간, 예약, 변경·취소, 상태 전이, 리마인더.
5. **결제 기록** — 외부 결제/계좌이체 확인을 포함한 상태 기록. 초기에는 결제금 직접 보관·정산을 하지 않는다.
6. **명식/엔진 브리핑** — 입력 검증, 명식 스냅샷, 계산 기준, 근거, 경고, 엔진 버전.
7. **상담 세션/노트** — 상담 전·중·후 상태, 내부 메모, 질문별 근거와 해석.
8. **리포트 발행** — 상담사 검수, 버전, 공개/비공개 문장, 공유 링크 만료, HTML/PDF.
9. **브랜드 설정** — 상담사명, 로고, 색상, 연락처, 서명, 리포트 템플릿.
10. **운영 지표** — 예약 전환, 노쇼, 준비 시간, 리포트 발행·열람, 재방문.

### 4.2 엔진과 플랫폼의 경계

**기존 엔진이 책임지는 것**

- 한국 법정시·DST·진태양시·자시 학파를 포함한 계산 정책
- 명식, 대운·세운, 오행·십신, 격국·용신, 합충형파해·신살 등 계산
- 주제별 근거, 패턴, 해석 초안, 시점 서사
- 계산 경고, `runId`, `inputHash`, 엔진·계약·데이터 버전
- Markdown/standalone HTML 렌더링의 기반

**새 플랫폼이 책임지는 것**

- 고객·상담사·워크스페이스·예약·결제·세션·리포트 저장
- 인증·권한·동의·삭제·감사 추적
- 엔진 실행을 고객/세션에 연결하고 당시 스냅샷을 보존
- 상담사 편집·검수·발행 상태 관리
- 알림, 공유 링크, 운영 지표, 외부 연동

**중요 원칙:** 엔진의 `runId`는 고객 이력이 아니다. 플랫폼은 별도의 `calculation_snapshot`과 `report_version`을 저장해야 한다.

## 5. MVP 정의

### 5.1 MVP 목표

첫 MVP는 예약 플랫폼 전체를 만들지 않는다. 목표는 다음 한 가지를 검증하는 것이다.

> **상담사가 한 고객의 상담 준비부터 검수된 리포트 발행까지 처리할 때, 기존 도구 조합보다 실제 시간을 줄이고 다시 사용할 의사가 있는가?**

### 5.2 MVP 포함 범위

MVP는 두 트랙으로 분리한다. **Track A가 핵심 가치 검증 대상**이고, Track B는 운영 수요를 확인하는 최소 실험이다. 예약·결제·알림을 일반적인 예약 SaaS 수준으로 확장하지 않는다.

#### Track A — 상담 준비→검수 리포트

#### P0-A 고객과 상담 준비

- 상담사 로그인 및 개인 워크스페이스
- 고객 생성/수정/검색/보관
- 출생정보, 출생지, 성별 등 엔진 입력과 시간 정확도 기록
- 개인정보 수집 목적·동의 시각·철회·삭제 요청 기록
- 상담 목적, 사전 질문, 예약 메모 입력
- 고객별 과거 세션/리포트 타임라인

#### P0-B 엔진 브리핑

- 고객 레코드에서 명식 계산 실행
- 시간 보정·불확실성·정책 경고 표시
- 계산 입력과 결과 스냅샷 저장
- 직업·재물·사업·연애·결혼·올해 운 등 주제별 근거 조회
- 근거와 초안 문장을 함께 보여주되 내부용/고객용을 분리
- 엔진 버전과 콘텐츠 상태를 기록
- `published` 콘텐츠가 아닌 문구는 고객용 자동 발행 경로에서 차단

#### P0-C 상담 세션과 리포트

- 세션 상태: `planned → prepared → in_progress → review → delivered → archived`
- 질문별 상담사 메모와 최종 해석 입력
- 자동 초안 수정·삭제·비공개 처리
- 상담 후 핵심 요약과 후속 메모
- 상담사 검수자·검수 시각 기록
- 브랜드 HTML/인쇄용 PDF 리포트 생성
- 만료 가능한 고객 공유 링크와 열람 상태
- 리포트 버전 생성 및 이전 버전 보존

#### Track B — 최소 예약/외부 결제 원장 실험

- 상담 서비스, 소요시간, 표시 가격, 한 가지 취소 정책 등록
- 상담사가 직접 입력하는 예약 생성·변경·취소
- 캘린더형 일정 조회와 중복 시간 경고
- 상태: `requested → confirmed → completed/cancelled/no_show`
- 결제는 **외부 거래의 수동 기록 모드만** 허용: `unpaid → recorded → refunded`
- 외부 거래 식별자, 금액, 확인자·확인 시각, 환불 사유·금액을 기록
- 고객에게 결제 링크를 제공하거나 PG 상태를 자동 확정하지 않음
- 알림은 베타 전 채널 하나와 발송 실패·수신 거부 처리를 결정한 뒤 추가

### 5.3 MVP 제외 범위

- 공개 상담사 검색·매칭·후기 마켓플레이스
- 자체 PG, 에스크로, 상담사 자동 정산
- 카카오/네이버/SMS 등 다중 알림 채널의 완성형 연동
- 패키지·구독권·반복 예약·쿠폰
- 다인 조직의 복잡한 배정·지점·역할별 정산
- 고객이 자동으로 운세를 생성하고 즉시 받는 소비자 서비스
- 자동 법률/의료/재무 판단 또는 결과 보증
- 전문가 검수 전 콘텐츠의 고객 공개

## 6. 핵심 데이터와 상태 요구사항

### 6.1 핵심 객체

| 객체 | 최소 필드/역할 |
|---|---|
| `workspace` | 상담사 소유 경계, 설정, 보존 정책 |
| `counselor` | 인증 주체, 프로필, 브랜드, 검수자 |
| `client` | 식별자, 연락처, 출생정보, 출생지, 동의/철회, 보존 상태 |
| `service` | 상담 유형, 소요시간, 표시 가격, intake, 취소 규칙 |
| `appointment` | 고객, 서비스, 일시, 상태, 채널, 취소 사유 |
| `payment_record` | 예약, 금액, 외부 거래 식별자, 상태, 확인자, 시각 |
| `session` | 예약 연결, 전·중·후 상태, 시작/종료, 메모 |
| `calculation_snapshot` | 정규화 입력, 계산 기준, 결과, 경고, 버전, 실행 시각 |
| `interpretation_draft` | 질문, 근거 참조, 자동 초안, 상담사 편집본, 공개 여부 |
| `report_version` | 렌더 입력, 검수자, 검수 시각, 발행 상태, 링크/만료 |
| `audit_event` | 주체, 행위, 대상, 시각, 결과, 요청 추적 ID |

### 6.2 불변성·이력

- 상담 리포트는 덮어쓰지 않고 새 버전을 만든다.
- 고객의 출생정보가 수정되면 기존 계산 스냅샷은 변경하지 않고 재계산한다.
- 상담 당시의 엔진·콘텐츠 버전을 결과에 고정한다.
- 결제 상태는 임의 삭제하지 않고 대사 가능한 이벤트 이력을 남긴다.
- 고객 삭제 요청은 법정 보존이 필요한 결제 기록과 상담 메모의 처리 결과를 분리해 기록한다.

## 7. 개인정보·신뢰·결제 요구사항

본 절은 법률 자문이 아니며 출시 전 국내 개인정보·전자상거래·전자금융 관련 검토가 필요하다.

### 7.1 개인정보 최소 기준

- 출생정보·연락처·상담 목적·상담 메모를 목적별로 분리해 최소 수집한다.
- 상담 메모에 주민등록번호, 의료정보, 금융정보 등 불필요한 민감정보를 입력하지 않도록 안내·탐지한다.
- 고객에게 수집 목적, 보유기간, 공유 대상, 삭제/열람 경로를 명확히 알린다.
- 상담사 워크스페이스 간 고객 데이터가 섞이지 않도록 모든 조회에 테넌트 경계를 강제한다.
- 고객 데이터와 파생 리포트의 접근 권한을 분리한다.
- 공유 링크는 무작위 토큰, 만료, 철회, 열람 로그를 갖는다. URL에 출생정보나 이름을 넣지 않는다.
- 백업·로그·분석 데이터에도 원문 메모가 불필요하게 복제되지 않도록 한다.
- export/delete 요청과 실제 처리 결과를 감사 이벤트로 남긴다.

### 7.2 역할별 기본 권한

| 역할 | 고객·예약 | 원국/근거 | 내부 메모 | 고객 리포트 | 결제 |
|---|---|---|---|---|---|
| 상담사 | 생성·수정 | 조회·실행 | 조회·수정 | 검수·발행·철회 | 기록·확인 |
| 고객 | 본인 입력·열람 요청 | 공개 범위만 | 불가 | 발행본만 | 본인 거래 안내 |
| 플랫폼 운영자 | 지원 목적 최소 접근 | 원칙적 불가 | 원칙적 불가 | 기술 지원 범위 | 지원·감사 |
| 향후 관리자 | 조직 범위 | 조직 범위 | 정책에 따른 제한 | 조직 범위 | 조직 범위 |

플랫폼 운영자는 기본적으로 상담 내용과 출생정보를 읽을 수 없어야 하며, 지원 접근이 필요한 경우 사유·승인·시각을 기록한다.

### 7.3 결제·환불 경계

초기 결제 기능은 “돈을 받는 시스템”이 아니라 “상담사가 외부 거래 상태를 운영상 추적하는 시스템”으로 정의한다.

- 결제수단과 직접 자금 보관 여부를 먼저 결정한다.
- PG 연동을 도입할 때 서버 검증, 웹훅 서명 검증, 중복 이벤트 멱등성, 금액·주문 대조, 환불 상태 대사를 구현한다.
- 예약 확정과 결제 확인의 관계를 서비스별로 설정한다.
- 예약금, 당일 취소, 노쇼, 부분 환불 규칙을 명시하고 상태 전이를 기록한다.
- 직접 중개·정산·에스크로를 시작하면 사업자 지위와 약관·세금·분쟁 대응을 다시 검토한다.

### 7.4 자동 생성 결과의 신뢰

- 자동 초안과 상담사 확정 문장을 UI와 저장 모델에서 구분한다.
- 자동 초안에는 계산 근거와 생성 시각·버전을 붙인다.
- 상담사가 문장을 수정·제외·거부할 수 있어야 한다.
- `반드시`, `보장`, `확실`, `100%` 같은 보증성 표현을 차단한다.
- 위험한 의료·법률·재무 판단을 단정하지 않고 필요 시 전문가 상담을 권한다.
- 고객에게는 “상담사 검수 완료” 상태인 문장만 발행한다.

## 8. 사용자 스토리와 수용 기준

### US-01 고객과 명식 준비

**상담사로서** 신규 고객의 출생정보와 상담 목적을 등록해 상담 전 준비 시간을 줄이고 싶다.

- 출생시간 미상/불확실성을 필수로 표시할 수 있다.
- 계산 기준과 경고가 결과에 보인다.
- 동일 고객의 기존 세션과 명식 스냅샷을 구분해 조회할 수 있다.

### US-02 질문 기반 브리핑

**상담사로서** ‘직업’ 또는 ‘올해 운’을 선택해 관련 근거와 초안을 한 번에 확인하고 싶다.

- 주제 선택 후 근거 출처·시점·관련 계산 결과가 표시된다.
- 근거와 고객용 표현을 분리해 수정할 수 있다.
- 상담사는 초안을 완전히 삭제하고 자신의 문장을 쓸 수 있다.

### US-03 상담 세션 기록

**상담사로서** 상담 중 메모와 상담 후 결론을 고객별 타임라인에 남기고 싶다.

- 세션 전/중/후 상태와 작성 시각을 저장한다.
- 내부 메모는 고객 리포트에 기본 포함되지 않는다.
- 중간 저장과 충돌 방지가 있어야 한다.

### US-04 검수 리포트 발행

**상담사로서** 내 브랜드로 검수한 리포트를 발행하고 싶다.

- 발행 전 체크리스트와 검수자·시각이 필요하다.
- 미검수 자동 문장이나 비공개 메모가 발행되지 않는다.
- 발행본은 버전으로 고정되고 공유 링크를 철회할 수 있다.

### US-05 예약과 결제 추적

**상담사로서** 예약 상태와 외부 결제 상태를 한 화면에서 관리하고 싶다.

- 중복 일정과 필수 예약정보 누락을 경고한다.
- 취소·노쇼·환불 상태와 사유를 기록한다.
- 결제 금액, 외부 거래 식별자, 확인자를 추적할 수 있다.

### US-06 고객의 정보 통제

**고객으로서** 내가 제출한 정보와 상담사가 발행한 리포트만 확인하고 삭제/철회를 요청하고 싶다.

- 고객용 링크는 만료·철회된다.
- 내부 메모·다른 고객 정보에 접근할 수 없다.
- 삭제/열람 요청의 접수와 처리 상태를 알 수 있다.

## 9. 단계별 로드맵

### 0단계 — 신뢰·콘텐츠 선행 조건

- 독립 사주 전문가 검수 시작
- 핵심 콘텐츠를 `reviewed`에서 `published`로 승격할 기준과 fixture 확정
- 상담사 인터뷰 5~10명, 실제 도구·시간·리포트 샘플 조사
- 개인정보 처리·보존·삭제·자동 생성 결과 정책 초안 작성

**통과 조건:** 전문가 검수 기준과 최소 발행 콘텐츠가 준비되고, 인터뷰에서 반복되는 핵심 작업과 시간 기준선이 확보됨.

### 1단계 — 내부 프로토타입: 준비→리포트

- 로그인 없이도 안전한 테스트 데이터로 고객·세션·엔진 스냅샷·질문·리포트 흐름 검증
- 기존 엔진 API를 서버 경계에 연결
- 상담사 편집·검수·HTML/PDF 발행
- 실제 상담사 2~3명 관찰 테스트

**통과 조건:** 상담사가 기존 방식으로 하던 샘플 상담을 처음부터 끝까지 수행하고, 치명적 계산/콘텐츠 오류 없이 작업 시간과 누락을 측정할 수 있음.

### 2단계 — 제한 베타: 예약 운영 추가

- 고객 접근, 초대/사전 입력, 예약 상태, 외부 결제 기록, 최소 리마인더
- 고객별 타임라인과 재상담
- 링크 철회, 삭제 요청, 감사 로그

**통과 조건:** 5~10명의 상담사가 실제 유료 상담 일부를 처리하고, 시간 절감·재사용·리포트 열람·오류 수정 데이터를 수집함.

### 3단계 — 운영 상품화

- PG 연동 여부 결정 및 구현
- 패키지·반복 예약·노쇼·환불 자동화
- 카카오/네이버/이메일/SMS 연동 우선순위 결정
- 가격·플랜·사용량 제한·지원 프로세스 확정

### 4단계 — 팀/성장 기능

- 다인 조직 권한·배정·지점·정산
- 상담사 브랜드 예약 페이지와 고객 유입
- 분석 대시보드와 후속관리 자동화
- 마켓플레이스는 별도의 사업성 검토 뒤 착수

## 10. 성공 지표와 검증 계획

### 10.1 핵심 지표

**Primary:** 활성 상담사가 한 상담을 `고객 준비 → 세션 기록 → 검수 리포트 발행`까지 완료하는 데 걸리는 중앙값 시간의 감소율.

제안 기준선은 인터뷰로 측정하고, 베타 목표는 **기존 방식 대비 30% 이상 감소**로 둔다. 기준선이 없으므로 현재 수치는 가설이다.

**Secondary:**

- 상담 전 준비 시간
- 상담 중 근거 조회/문서 전환 횟수
- 상담 후 리포트 작성 시간
- 세션 완료율과 리포트 발행률
- 7일 내 재사용률, 4주 유지율
- 초안 수정·삭제율 및 상담사 최종 검수율
- 고객 리포트 열람률·링크 철회율
- 예약 취소·노쇼·재예약 비율

**Guardrail:**

- 계산/시간 보정 오류 0건 목표 및 전문가 신고 오류 처리시간
- 미검수 문장 고객 발행 0건
- 테넌트 간 데이터 노출 0건
- 삭제·철회 요청 미처리 0건
- 결제 상태 불일치와 중복 처리 0건
- 상담사가 엔진 결과를 과신해 수정 없이 발행하는 비율의 모니터링

### 10.2 상담사 인터뷰 계획

**대상:** 1인 상담사 5~10명. 초보/중견, 온라인/대면, 리포트 제공 여부, 월 상담량을 다양하게 구성한다.

**관찰 과제:** 실제 개인정보 대신 테스트 고객으로 다음을 재현한다.

1. 신규 고객 접수와 출생정보 확인
2. 상담 목적별 준비
3. 상담 중 질문 전환 및 근거 재조회
4. 상담 후 메모와 고객용 리포트 작성
5. 기존 고객 재상담 준비
6. 예약 변경·취소·결제 확인 처리

**측정:** 각 작업의 시작/종료 시각, 도구 전환 횟수, 검색 실패, 재입력, 누락, 수정 횟수, 말로 표현한 불안과 신뢰 요인을 기록한다.

**검증 질문:**

- 어떤 단계에서 실제로 만세력책/참고서/메신저를 오가는가?
- 상담 중 가장 자주 다시 찾는 근거는 무엇인가?
- 자동 초안에서 절대 위임할 수 없는 판단은 무엇인가?
- 리포트에 넣는 정보와 내부 메모로 남기는 정보는 어떻게 다른가?
- 현재 예약·결제·환불을 어떤 조합으로 관리하는가?
- 월 얼마를 지불하면 기존 도구보다 편리하다고 느끼는가?

### 10.3 베타 실험

- 상담사 5~10명, 2~4주, 실제 상담 일부만 사용
- 첫 주는 준비·리포트, 둘째 주부터 예약·결제 기록 추가
- 대조군이 어려우면 각 상담사의 기존 방식과 베타 방식을 교차 비교
- 매 상담 후 3분 설문: 시간, 신뢰, 수정 필요, 다시 쓸 의향
- 주간 인터뷰: 누락 데이터, 오류, 고객 반응, 결제/예약 불편

**계속할 조건:** 시간 30% 감소, 리포트 발행률 상승, 치명적 오류 0, 4주 재사용 의향 70% 이상.

**중단/수정 조건:** 계산 기준 혼동, 자동 문장 과신, 고객 데이터 불안, 예약 상태 불일치가 반복되거나 핵심 사용자가 준비 화면보다 기존 도구를 선호함.

## 11. 수익모델 가설

초기에는 거래액 수수료보다 **상담사 워크스페이스 구독**이 제품 가치와 법적 운영 범위를 단순하게 유지한다.

1. **Solo 구독:** 상담사 1명, 고객/세션/리포트 한도, 기본 브랜드.
2. **Pro 구독:** 더 많은 리포트, 고급 브리핑, 브랜드 커스터마이징, 운영 지표.
3. **Team 구독:** 다인 권한·배정·조직 분석. 초기 MVP에는 판매하지 않는다.
4. **사용량 과금 후보:** 리포트 발행량·고급 엔진 실행량. 단, 가격 예측 가능성을 해치지 않는지 검증한다.
5. **초기 베타:** 유료 전환 의향과 가격 민감도 확인을 위한 제한된 유료 파일럿.

예약 결제에 대한 거래 수수료는 PG·환불·정산·분쟁 부담이 실제로 확인된 후 별도 결정한다. 가격은 경쟁사 가격표를 복사하지 않고 상담 시간 절감과 리포트 매출 영향에 대한 인터뷰로 정한다.

## 12. 리스크와 미결정 사항

### 높은 위험

- 전문가 검수 전 콘텐츠를 제품 가치로 약속하는 위험
- 시간 보정·출생시간 불확실성에 대한 상담사 신뢰 실패
- 출생정보·상담 메모·결제정보의 테넌트 혼합 또는 과도한 운영자 접근
- 자동 생성 문장의 고객 오해·과신
- 직접 결제·정산을 시작하면서 사업자 지위·환불·세무 책임이 커지는 위험

### 아직 결정하지 않은 것

- 고객이 출생정보를 직접 입력할지, 상담사가 대리 입력할지
- 온라인 예약 페이지를 MVP에 넣을지, 상담사가 예약을 직접 기록할지
- 이메일만으로 시작할지 국내 메신저/문자 연동을 먼저 할지
- DB/배포/인증/결제 제공자와 국내 데이터 처리 위치
- 고객 리포트 PDF 다운로드를 허용할지, 만료 링크만 제공할지
- 상담 메모 보존 기간과 유료 플랜별 보존 정책
- `published` 콘텐츠가 충분하지 않을 때 베타에서 어떤 기능만 허용할지

## 13. 리서치 검토 후 보강할 P0 결정사항

독립 검토에서 다음 항목을 MVP의 구현 전 게이트로 추가했다.

- 개인정보 처리 주체, 처리위탁, 국외 이전, 하위 처리자와 고객 고지 책임
- 미성년자·법정대리인·상담사 대리 입력을 포함한 `data_subject`와 `entered_by` 구분
- 열람·정정·삭제·처리정지 요청의 본인 확인, 처리 기한, 보존 예외, 백업·검색 인덱스 처리
- 운영자 MFA와 긴급 지원 접근의 사유·승인·사후 검토, 원문 다운로드 제한
- 자동 초안의 모델/프롬프트/콘텐츠 버전, AI 제공자 전송 여부, 학습 재사용 금지, 오류 신고·사람 검토 전환
- 공유 리포트 본인 확인 방식, 다운로드 허용 여부, PDF 철회 불가 고지·워터마크
- 콘텐츠 `published` 최소 범위, 학파 차이·계산 오류·정책 선택의 분류, 롤백과 기발행 리포트 재검토
- 예약 채널·타임존·재예약·알림 실패·수신 거부를 Track B에 넣을지 여부

이 보강사항 때문에 현재 문서는 구현 명세가 아니라 **인터뷰·법무·보안 검토를 앞둔 discovery PRD**로 취급한다.

## 14. 근거와 가설의 구분

이 문서의 다음 내용은 성격이 서로 다르다.

- **확인된 사실:** 공개 공식 자료에서 확인한 예약·결제·상담 전후 업무 단위, 현재 저장소의 엔진·해석·렌더러 구현 상태.
- **제품 가설:** 상담사가 근거-초안-검수 흐름과 고객 타임라인을 유료 가치로 느낄 것이라는 판단, 초기 ICP를 1인 상담사로 두는 것, 준비부터 리포트까지 30% 시간 절감 목표.
- **설계 제안:** MVP 객체·상태·권한·로드맵과 결제 경계. 인터뷰·법률 검토·보안 설계로 확정해야 한다.

경쟁 제품의 공개 페이지에서 특정 기능을 찾지 못했다는 사실은 그 기능이 존재하지 않는다는 증거가 아니다. 마찬가지로 이 PRD의 권한·보존·삭제 정책은 출시 전 법률 자문과 기술 위협 모델링을 대체하지 않는다.

## 15. 구현 전 의사결정 게이트

다음 항목은 UI를 본격 구현하기 전에 확정한다.

- [ ] 독립 전문가 검수자와 검수 일정
- [ ] 초기 1인 상담사 인터뷰 대상 5~10명
- [ ] 실제 업무 시간 기준선과 샘플 상담 시나리오
- [ ] `published` 콘텐츠 최소 범위
- [ ] 개인정보 처리 주체·위탁 구조·국외 이전 및 하위 처리자
- [ ] 미성년자·법정대리인·상담사 대리 입력 정책
- [ ] 고객 데이터 보존·삭제·열람·정정·처리정지 요청의 운영 절차
- [ ] 운영자 break-glass 접근, MFA, 다운로드 제한, 감사 로그 검토
- [ ] AI/자동 초안의 모델·프롬프트 버전, 전송·학습 재사용·보존 정책
- [ ] 콘텐츠 주제별 `published` 최소 커버리지·롤백·기발행 리포트 재검토
- [ ] MVP 결제 경계: 수동 외부 거래 기록으로 고정할지 여부
- [ ] 서버/API/인증/데이터베이스 기술 선택
- [ ] 고객 리포트 발행 승인 상태와 공유 링크 정책
- [ ] 계산 스냅샷·리포트 버전의 저장 계약
- [ ] 베타 오류 대응·전문가 수정·콘텐츠 롤백 절차

**이 게이트가 통과되기 전에는 예쁜 예약 화면보다 데이터 경계, 검수 흐름, 계산 결과의 재현성을 먼저 구현한다.**
